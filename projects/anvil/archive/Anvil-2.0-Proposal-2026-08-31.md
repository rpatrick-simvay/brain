## Verified stack (v0.2 inputs)
Proxmox VE fleet: PVE-Terraform creates VMs/disks/tags (Ansible never does); PVE-Ansible converges via Base→Storage→Engine→Verify layers, dynamic inventory from Proxmox VM tags, dev/prod share one node split by env tag, no addresses or secrets in git, nftables per-group rules from a fleet document (PVE-Terraform/environments/fleet.yml), no containers, verify.yml passes only with zero changed tasks. Engines: ClickHouse (only datastore; databases raw/marts/dims; least-privilege users like dlt_writer INSERT-only), PostgreSQL (postgres_<app> child groups), Grafana (git-synced dashboards; alert rules on ClickHouse notify PagerDuty webhook directly; no Alertmanager, no VictoriaMetrics, no host metrics), n8n, Dagster (uv+systemd, Postgres run storage). Secrets: Bitwarden Secrets Manager only; per-host machine token, in-guest `bws run`. Data platform (simvay-platform): dlt→ClickHouse→dbt→Grafana, Dagster-orchestrated, per-client fan-out, rolling-window idempotent loads; S1 source done, live validation in progress. Fleet status: nothing has run against real hosts yet; backup strategy undecided (backup_verify.yml fails by design).

## Recommendation (v0.3)
1. **Anvil control plane on the fleet**: new PVE-Ansible roles (anvil_api, anvil_portal, anvil_eval, minio) + fleet-document/Terraform entries. FastAPI + React/xterm.js portal; job state in postgres_anvil; Anvil databases + least-privilege users on the shared ClickHouse; MinIO (new engine role, object lock) for evidence bytes. Dashboards/alerts are NOT portal code: Grafana rules over Anvil marts → PagerDuty.
2. **Ephemeral Windows runners**: golden template (Packer + anvil_runner role; pinned pwsh/modules, hashed collectors, agent, Cloudbase-Init) → linked clone per analyst session into a fenced `anvil-runners` Proxmox resource pool via a scoped API token (clone/destroy only; the agreed carve-out from the Terraform-only rule), one-time bootstrap token, outbound WSS, console passthrough unchanged, evidence uploaded, clone destroyed (TTL reaper, default 8h; warm pool for latency). Nothing persists. Persistent runner kept as fallback A1 (same protocol). Linux ephemeral runner later for the 9 REST-only collectors.
3. **Client credential vault (v0.3)**: client API keys (the 9 API-token sources + GWS service-account key) live in a dedicated `anvil-clients` Bitwarden project. Analyst writes a key once via a masked write-only Credentials page; API stores only the secret UUID + metadata (who/when/last rotated/last used/verified) in Postgres; "Test credential" probe verifies without echoing; runner fetches at job time and injects as SecureString/temp file that dies with the clone; per-fetch audit rows; rotate = overwrite, offboard = revoke client prefix; Grafana alert on unrotated >180d. Honest limit: BWS has no write-only grant, so "never viewable" is enforced at the Anvil layer (no read route, write-only UI, project locked to Anvil machine accounts) with a Bitwarden org admin as the audited residual (event-log alert on console reads). Per-client consent recorded in the profile; console prompting stays as the fallback for clients that decline; M365 stays device-code interactive; ADGP stays run package. Moves vaulting from Phase 4 into Phase 2 core; Phase 4 scheduling becomes just a Dagster scheduling + consent question.
4. **Evaluation service** (Claude API, existing prompt/schema) and **Blacksmith staging package** unchanged from v0.1; Complete checkbox stays human.
Boundary kept: dlt pipeline data is never compliance evidence; evidence stays point-in-time hashed collector snapshots (convergence is a Phase 4+ study item only).
