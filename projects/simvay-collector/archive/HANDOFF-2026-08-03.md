## 1. One-paragraph summary

Simvay is building a deployable VM appliance — the **Simvay Collector** — that receives syslog from
client network devices and forwards it, parsed, into that client's SentinelOne Singularity Data Lake.
The forwarding engine is a three-container Docker stack published by SentinelOne; the appliance wraps
it with an OS, unattended build automation, a browser-based setup console, a self-test, a watchdog
and a status page so a site deployment is repeatable rather than hand-built. **Phase 1 (prove the
collector) is complete and evidenced. Phase 2 (golden image) is now essentially complete** — the
unattended build works end to end and has been run four times. What remains is testing the final
image, sealing it, and packaging the OVA.

**Product name:** *Simvay Collector*. It is a modified SentinelOne collector; "SentinelOne" is
reserved for the actual SentinelOne product (Data Lake, agent, console, upstream container images).

### The ten bugs found and fixed during the golden-image work

| # | File | Bug | Fix |
|---|---|---|---|
| 1 | `make-gold-iso.sh` | `systemctl enable` in cloud-init `runcmd` scheduled the build for the *next* boot, so it never ran during the install | `enable --now` |
| 2 | `provision.sh` | `apt-get install hyperv-daemons` — that is the RHEL/Fedora name. Ubuntu ships `linux-cloud-tools-virtual` / `linux-tools-virtual`. | 3 | `make-gold-iso.sh` | `gold-build.sh` shreds `kit.tgz.b64` after unpacking, so restarting the unit died instantly on a missing file; the spool step would have run `pvcreate -ff` against a live `/var/lib/docker` on a re-run | both steps made idempotent |
| 4 | `provision.sh`, `s1-collector-firstboot` | Hyper-V daemons `BindTo` `/dev/vmbus` device units that never appear under VMware → 90-second device timeout and a red `DEPEND` failure on **every boot** | masked at build; firstboot unmasks and enables them only when `systemd-detect-virt` returns `microsoft` |
| 5 | `s1-collector-selftest` | An unconfigured appliance reported `RESULT: FAILED — Not ingesting` across five checks, and `spool-volume` **passed on an empty path** | new `skip` state, `RESULT: NOT CONFIGURED`, exit 0, 2 s instead of ~40 s; `spool-volume` warns instead of false-passing |
| 6 | `provision.sh` | **The worst one.** ufw allowed only 22/tcp, never 8443. The setup console is the only way the appliance is configured, and `s1-collector-configure` (which opens 8443) is driven *from* that console. Every fresh deployment deadlocked | `ufw allow 8443/tcp` in the golden image, plus two gates (below) |
| 7 | `s1-collector-web` | Status page rendered `Spool volume: ? used of ? on ?` on every fresh appliance — the Docker named volume does not exist until the stack first starts | falls back to the filesystem backing `/var/lib/docker` |
| 8 | `s1-collector-web` | `Watchdog: unknown` before the health timer first fires | reads `waiting for first check` |
| 9 | `s1-collector-web` | The forced first passphrase change asked for the factory passphrase the analyst had typed one redirect earlier | current-passphrase field dropped **only** when `is_factory_passphrase()`; kept for later changes, where it stops someone at an unattended signed-in browser locking the owner out. | 10 | `s1-collector-console`, `s1-collector-firstboot`, `gold-build.sh` | The banner advertised `https://<ip>:8443/` **before the web service could accept connections**. | 11 | `s1-collector-firstboot` | **What broke the demo OVA.** Step 5 ran `systemctl restart systemd-timesyncd` — `provision.sh` installs chrony, which displaces timesyncd on Ubuntu, so the unit does not exist. | 11b | `s1-collector-firstboot` | `hostnamectl set-hostname` and `netplan apply` were unguarded — the same landmine waiting to go off | both now warn instead of aborting |
| 11c | `s1-collector-firstboot` | Nothing guaranteed the setup console came up if an earlier step still died | an `EXIT` trap enables `s1-collector-web`, waits for port 8443 and renders the banner regardless of where first boot failed |
| — | `s1-collector-seal` | `rm -rf /var/lib/s1-collector/*` is a glob and does not match dotfiles — `.firstboot-done` is one. Left behind, `ConditionPathExists` never fires and firstboot never runs on the clone. Latent, not the demo failure, but real | `find /var/lib/s1-collector -mindepth 1 -delete`; seal now refuses to finish if the marker survives |

**Bugs 5, 7, 8 and 10 are the same failure**: the appliance could not distinguish *"not ready yet"*
from *"broken."* Bug 11 is a different, third instance of a different pattern: **an optional step
aborting the whole run under `set -e`** — `hyperv-daemons` (bug 2) was the first, `hostnamectl`/
`netplan apply` (11b) would have been the next. The `EXIT` trap (11c) is the class fix — it does not
prevent the failure, it guarantees the console comes up anyway. If you find a fifth instance of
either pattern, fix it the same way.

### Two gates so bug 6 cannot come back

- **Build time** — `make-gold-iso.sh` greps `provision.sh` for `^ufw allow 8443/tcp` and refuses to
  build the ISO without it. Fails in a second rather than 40 minutes into a build.
- **Run time** — `provision.sh` ends with `ufw status | grep -qE '^8443/tcp[[:space:]]+ALLOW'` and
  fails the build if the rule did not take.

Both verified by sabotage. **A completed build is therefore proof that 8443 is open.** If the console
is unreachable on a VM whose build finished, the cause is *not* ufw — check the certificate warning,
the readiness window (bug 10), and the network path, in that order.

`gold-build.sh` also warns loudly in the build log when the spool disk is not larger than the root
disk — the two-same-size-disks trap that cost a cycle.

## 4. TEST THE IMAGE — do this before sealing

The VM must be built from **seed v8** with **disk 1 = 80 GB and disk 2 = 100 GB**. If the two disks
are the same size the spool lands on the wrong one silently; only the size in the build report gives
it away.

**Create the VM at compatibility "ESXi 7.0 U2 and later" (hardware version vmx-19)** — decision
2026-08-03 (Ryan). That makes ESXi 7.0 U2 the legitimate supported floor of the shipped OVA. The
floor is set HERE, at VM creation: a hardware version cannot be relabelled in the OVF afterwards
(§5, the pciRootBridge lesson). Verify in the host client VM summary before starting the build:
"Compatibility: ESXi 7.0 U2 and later (VM version 19)".

### 4.1 Build-level checks — over SSH, not the ESXi console

```
ssh simvay@<vm-ip>
```

**Do not use the ESXi web console for anything but reading.** It drops the Shift key on synthetic
keystrokes, so a `sed` typed there silently corrupts the file. `ssh` is installed and password auth
is enabled by the autoinstall; `scp` from PowerShell is the clean way to move a file onto the VM.

```bash
sudo cat /root/GOLD-BUILD-REPORT.txt
lsblk
findmnt /var/lib/docker
sudo ufw status verbose
hostname
command -v vmtoolsd
ls -l /opt/simvay/action1-agent.deb
sudo grep -iE "warning|refusing|error" /var/log/simvay-gold-build.log
```

Expected:

| Check | Pass looks like | Fail looks like |
|---|---|---|
| `firmware:` in the report | `EFI` | `BIOS` — the fleet is locked to Hyper-V Gen 1. Rebuild with EFI |
| `dockerfs:` in the report | ~`102000000k` | `81983896k` — spool landed on the 80 GB disk. Disks are transposed |
| `images:` in the report | `3` | fewer — the pre-pull failed, clients will need registry access at first boot |
| `web:` in the report | `active` | anything else — the console will not come up |
| `findmnt /var/lib/docker` | `/dev/mapper/vg_docker-lv_docker` | root filesystem — a stalled upload can fill `/` |
| `ufw status` | `22/tcp ALLOW` **and** `8443/tcp ALLOW` | 8443 missing — impossible if the build completed; suspect a stale seed |
| `hostname` on the built master | `s1collector-gold` | anything else — check `s1-collector-seal`'s hostname-reset step |
| `vmtoolsd` | present, non-empty path | missing — impossible on a completed v8+ build; `provision.sh` refuses to build without it |
| `action1-agent.deb` | present, non-zero | missing — check the build log for the Action1 warning |
| build log greps | only the expected Action1/optional warnings | `REFUSING TO BUILD` — the build aborted, do not seal |

Do **not** run `systemctl is-enabled hv-kvp-daemon.service hv-vss-daemon.service
hv-fcopy-daemon.service` against a v8+ image. Hyper-V support and those units are gone (§7) — the
check now fails on a *correct* build, not a broken one.

After seal, export and deploy a clone: `hostname` should read `simvay-collector-<6 hex of
machine-id>`, generated fresh by firstboot because `S1_HOSTNAME` is empty and the sealed hostname
(`s1collector-gold`) matches the factory pattern. Two clones on the same network must show two
different generated hostnames.

Passphrase change flow: the only rule left is **15 characters minimum** — no word-count, no
lowercase requirement. A single 15-character non-phrase string must be accepted.

### 4.2 Appliance behaviour

```bash
sudo s1-collector-selftest
```

Expect **`RESULT: NOT CONFIGURED`** and exit 0, with five `SKIP` lines. That is correct on a gold
image — the stack only starts when `s1-collector-configure` runs with a write key. A red
`RESULT: FAILED` here means something regressed in bug 5's fix.

### 4.3 The console banner — the analyst's first impression

Log out (`exit`) and look at the VM console in ESXi. `/etc/issue` renders **above** the `login:`
prompt, so it is invisible inside a session that is already logged in.

Expect the Simvay mark, `CONFIGURE THIS APPLIANCE FROM A WEB BROWSER`, the HTTPS URL, and a
four-word factory passphrase. If it says `SETUP CONSOLE IS STARTING`, wait — that screen refreshes
itself and is bug 10's fix doing its job.

### 4.4 The setup console

Open `https://<vm-ip>:8443/` in a browser.

**The first connection shows a certificate warning.** It is self-signed, and the appliance has no
public DNS name. Click Advanced → Proceed. This looks exactly like a firewall block and has misled
both a human and an AI session on this project — do not start debugging the network over it.

Signed out, the page should show **only** hostname, address and uptime, with the self-test collapsed
and a `Sign in to configure` button on the banner row. Everything else is behind the session by
design: destination, listeners, container count and spool state describe customer log topology.

Sign in with the factory passphrase. It should force a passphrase change **without** asking for the
factory passphrase again. Set a new one — capitals and symbols are accepted.

Then walk Network → Data Lake → Sources → Apply against the NFR tenant and confirm the self-test goes
all-pass. **If you do this, you must undo it before sealing** — see 4.5.

### 4.5 Before sealing

`s1-collector-seal` purges the web passphrase, TLS key, `setup.json`, `syslog.yaml`, Docker volumes,
machine-id, SSH host keys, logs and shell history. It is designed to be run on a configured
appliance. It **aborts if the SentinelOne agent is running** — that is intentional.

If the SentinelOne agent is to be baked in, install it **now**, last, and never start it:

```bash
sudo dpkg -i SentinelAgent_linux_*.deb
sudo /opt/sentinelone/bin/sentinelctl management token set <SIMVAY_SITE_TOKEN>
# do NOT run 'sentinelctl control start'
```

Per KB 000005482 the Linux agent generates its UUID at OS boot; activating it on the master gives
every collector Simvay ever ships the same identity. `s1-collector-firstboot` runs
`sentinelctl management uuid reset` and starts it on the clone.

Then:

```bash
sudo s1-collector-seal
sudo poweroff
```

**Halt, never reboot.** A reboot after sealing regenerates the identity material you just cleared.

## 5. PACKAGE THE OVA

The OVA version is now **1.0.1** (`simvay-collector-1.0.1.ova`). **1.0.0 is dead — it carries bug
11 and must never be deployed.**

**The export path that actually worked is the ESXi host-client GUI export, not `ovftool`'s `vi://`
path.** `vi://` failed on authentication — ESXi locks an account for 15 minutes after 5 failed
logins, and an already-open host-client session hides the lockout, so `ovftool` gets refused while
the GUI keeps working. **Follow `ovf/README.md` for the real, current procedure** (GUI export,
file-size fixes, ProductSection injection via `Inject-ProductSection.ps1`, manifest regeneration,
repack). §5.1–5.3 below describe the `vi://` path this project moved away from; keep them only as a
fallback if the GUI export is unavailable.

Run from a Windows workstation with `ovftool` installed
(developer.broadcom.com/tools/open-virtualization-format-ovf-tool/latest — free, account required).

The VM must be **powered off** and sealed.

### 5.1 Export the sealed VM to OVF

```powershell
cd "C:\Users\RyanP\Simvay Systems\SecurityOperationsHub - Documents\INTERNAL\03 - Projects\SentinelOne Collector\ovf"

ovftool --noSSLVerify --acceptAllEulas --diskMode=thin `
  "vi://root@10.10.75.10/<VM NAME>" .\s1collector.ovf
```

`<VM NAME>` must match the ESXi inventory name exactly. It has been renamed at least once — check
the host client first. **If the name contains a space, the quotes above are required.** Renaming the
VM to `SIMVAY-S1COLLECTOR-GOLD` before exporting avoids the problem entirely.

This produces `s1collector.ovf`, `s1collector-disk1.vmdk`, `s1collector-disk2.vmdk` and
`s1collector.mf`.

### 5.2 Inject the ProductSection

Follow **§3 of `docs/Simvay-Collector-OVA-Validation-Guide.pdf`** and merge
`ovf/product-section.xml` into `s1collector.ovf`. `ovf/export-and-repack.sh` automates the same
steps if you prefer.

The ProductSection is what gives vCenter deployments the pre-fill fields. It is optional to the
appliance — everything it supplies can be typed into the browser — but a vCenter deployment without
it means the analyst types more.

**The manifest is invalidated the moment you edit the OVF.** Either delete `s1collector.mf` before
repacking or let `ovftool` regenerate it; a stale manifest fails the import with a checksum error
that reads like a corrupt download.

### 5.3 Repack as an OVA

```powershell
ovftool --allowExtraConfig --acceptAllEulas .\s1collector.ovf .\simvay-collector-1.0.1.ova
```

`--allowExtraConfig` is required because the VM carries extra config keys; without it the repack
fails.

### 5.4 Validate the OVA by deploying it

**This is the test that matters.** Follow **§5A of the validation guide** — deploy the OVA to the
ESXi host as an analyst would, with no prior knowledge, and time it. Watch specifically for:

1. Does the console banner show the URL and passphrase, and only once the console is answering?
2. Does the certificate warning stop anyone?
3. Does the appliance get a DHCP lease and show a usable address?
4. Does the self-test say `NOT CONFIGURED` rather than `FAILED`?
5. Does a write key plus one source get it ingesting, without SSH?

**Deploy it twice, on the same network at the same time,** and confirm the two clones have different
machine-ids, different SSH host keys, different web passphrases, different hostnames
(`simvay-collector-<hex>` must differ) and different SentinelOne/Action1 agent identities. That is

## 6. Validation rules — audited against SentinelOne KB 000008665

The setup console's input validation was over-restrictive, and some of it came from an AI session's
own tooling limits rather than from the product. Audited 2026-08-03 against the SentinelOne KB
article "SentinelOne Collector for Syslog" (community.sentinelone.com, article **000008665** —
login-gated, no public snapshot).

| Rule | Verdict | Now |
|---|---|---|
| Passphrase must be lowercase | **Wrong.** Justified by "the ESXi console drops Shift" — that happens on *synthetic* keystrokes only. A person typing at the console types capitals fine | removed |
| Passphrase ≥16 chars **and** ≥4 words | **Over-restrictive.** Rejected strong non-phrase passphrases (e.g. a 20-char password-manager string) for no security gain (Ryan, 2026-08-03) | **only remaining rule: 15-character minimum.** Factory four-word phrases (min 19 chars) still clear it easily |
| Collector `name` lowercase-hyphen, 32 chars | **Over-restrictive.** The KB documents a free-form string; its example is `deployment-1` | `^[A-Za-z0-9](?:[A-Za-z0-9 ._-]{0,62}[A-Za-z0-9._-])?$` |
| Source names forced lowercase | **Over-restrictive.** Free string; lowercase-hyphen is convention, not a rule | same regex |
| Matcher glob limited to digits, dots and `*` | **Wrong.** The KB's own examples `router*`, `ap-*`, `firewall*`, `PA-*` were all rejected | validated per attribute |
| Console offered `srcip` only | **Missing four of five.** The KB supports `proto`, `srcip`, `destport`, `hostname`, `appname` — and the shipped `sources.d` fragments already use `hostname` and `appname` | all five, in a dropdown |
| Parser names may contain uppercase | **Correct** — real parsers are camelCase: `ciscoRouter`, `ciscoFirewall`, `agentSyslog` | kept |
| Port spec, `rfc3164`/`rfc5424` only | **Correct**, matches the KB exactly | kept |
| CIDR → glob conversion | **Correct** — the KB supports glob only, so converting is a kindness | kept |
| Appliance hostname lowercase | **Fine** — OS convention, and it lowercases input rather than rejecting it | kept |

Names and matchers are now double-quoted in the generated YAML, since a name may legally contain
spaces or dots.

### KB facts worth not rediscovering

- `matchers:` is a **list** of `{attribute, matcher}` pairs. A bare `matcher:` key is silently
  ignored by the config generator and yields a source-type with no matchers — a catch-all that claims
  every message. The shipped fragments use the correct form; keep it that way.
- Multiple matchers within one source-type are **ANDed**. Sources are applied most-specific first.
- Events matching nothing fall back to the `agentSyslog` parser.
- **Parser names are not validated by the collector at all.** A typo ships events tagged with a
  parser that does not exist and fails server-side, silently. This is acceptable to Simvay because
  custom parsers are built and named in the tenant.
- `syslog.crt` and `syslog.key` must sit beside `syslog.yaml` **even when no TLS port is configured**
  — the container entrypoint exits 1 without them.
- `destination` in the KB examples is written without a scheme (`xdr.us1.sentinelone.net`).

## 7. Decisions already made — do not relitigate without reason

Corrections from 2026-08-03 are marked **[revised]**.

| Decision | Why |
|---|---|
| **Browser-first configuration** | Only vCenter can deliver OVF properties. A browser works on every hypervisor |
| **Ubuntu 24.04 for the golden image**, not 26.04 | Action1 documents 22.04/24.04 only; S1 agent support for 26.04 unverified |
| **EFI firmware on the master** | This is a VMware EFI appliance regardless (`ovf/README.md`). **[revised 2026-08-03]** The original "Hyper-V Gen 2" half of this reasoning is moot — Hyper-V dropped, VMware only, `open-vm-tools` hard-gated at build; a purpose-built Hyper-V VM may follow later |
| **Netplan matches NICs by glob**, never by name | VMXNET3 gives `ens192`. Hyper-V-motivated originally, kept anyway — harmless on VMware and not worth destabilising |
| **[revised 2026-08-03]** Hyper-V dropped — VMware only, `open-vm-tools` hard-gated at build; purpose-built Hyper-V VM later | The old dual guest-tools install (`linux-cloud-tools-virtual` / `linux-tools-virtual`) and the `hv-*` masking loop are **deleted**, not masked — they produced bugs 2 and 4 and there is no longer a target for them to guard. `open-vm-tools` alone is a hard build gate: `provision.sh` refuses to build if `vmtoolsd` is missing, same philosophy as the ufw 8443 gate |
| **Spool disk found by shape, not `/dev/sdb`** | Device ordering differs on Hyper-V. Hyper-V-motivated originally, kept anyway — also correct on VMware |
| **[revised]** Generated secrets are lowercase four-word phrases | Readability off a console screen, **not** a Shift limitation. The Shift problem affects synthetic keystrokes only. Users may set any passphrase they like, subject only to the 15-character minimum (Ryan, 2026-08-03) — the old 16-char/4-word rule is gone |
| **One collector per client** | The config format holds exactly one tenant key. Architectural |
| **Disk 2 mounts at `/var/lib/docker`** | The spool is a Docker named volume |
| **[revised]** Match Meraki on `srcip` | Meraki's message body starts with an epoch timestamp where a hostname belongs, so `hostname` matching fails *silently* **against Meraki**. Cisco, VMware and others parse a hostname normally — all five attributes are available and correct to use |
| **One source-type per subnet** | Matchers within a source-type are ANDed |
| **Per-port syslog format** | Meraki (RFC 3164) and Veeam (RFC 5424) both default to port 514 |
| **S1 agent installed last, never activated on the master** | KB 000005482 — the Linux agent generates its UUID at boot |
| **Action1 package baked at build, installed on the clone** | Action1 claims an agent identity on first run. The build stages `/opt/simvay/action1-agent.deb`; firstboot installs and registers it per clone |
| **Setup console has no external dependencies** | An appliance on an isolated VLAN must still render its own diagnostics |
| **Write key entered in the browser only** | It never reaches a command line, seed ISO, datastore or shell history |
| **The status page is public, the setup pages are not** | On-site IT must be able to confirm the box is alive without credentials — but only hostname, address and uptime. Destination, listeners and spool state are customer topology and sit behind the session |
| **Default hostname is generated unique per clone** (`simvay-collector-<6 hex of machine-id>`) | A fleet sharing one hostname collides in DNS and is indistinguishable by `serverHost` in the Data Lake. An `s1.hostname` OVF property override still wins when a deployer sets one; the ProductSection default is now blank so it does not fight the generator. `s1-collector-seal` resets the hostname to `s1collector-gold` before export so the master's own generated name never ships |
| **OVA version 1.0.1** | 1.0.0 is dead — it carries bug 11 (chrony/timesyncd first-boot death) and was never actually deployed to a client. Never build or ship it |
| **Master built at hardware version vmx-19 — ESXi 7.0 U2 is the supported floor** (2026-08-03, Ryan) | The floor is set at VM creation, not in the OVF: relabelling `vmx-21` → `vmx-15` after the fact produced an OVA that imported and then failed to power on (`pciRootBridge` unsupported). Building at vmx-19 makes the exported `<vssd:VirtualSystemType>` legitimately `vmx-19` — never relabel it in either direction. Everything the appliance uses (EFI, pvscsi, VMXNET3) is well below v19 |

## 11. Known traps

- **The ESXi browser console drops the Shift key** on synthetic keystrokes — automation only, a human
  is fine. It also swallows Ctrl-C sent from browser automation. **Use SSH for anything beyond
  reading**; a `sed` typed into that console will silently corrupt the file it edits.
- **A certificate warning and a blocked port look identical.** Both give a blank failed page. Check
  whether the TCP connection succeeded before touching a firewall rule.
- **`web: active` in the build report does not mean reachable.** It means the service is running. It
  was `active` throughout the ufw deadlock.
- **A completed build proves 8443 is open** — the run-time gate guarantees it. Rule ufw out
  immediately and look elsewhere.
- **The spool is a Docker volume**, not the host directory of the same name.
- **A rejected write key is silent.** Containers stay up, ports stay bound, nothing arrives. Only the
  self-test's authentication check catches it.
- **Two same-size disks put the spool on the wrong one silently.** `findmnt` still looks correct; only
  the size in the build report reveals it. `gold-build.sh` now warns in the log.
- **`--X:injectOvfEnv` requires `--powerOn`.** Without it, properties are silently dropped.
- **Editing the OVF invalidates the manifest.** Delete `s1collector.mf` or regenerate it.
- **Meraki syslog is a per-network setting.** Enabling it on one device enables it for the whole
  network — expect several source IPs from one change.
- **Meraki transport is limited by the least capable device.** An MX on 26.1+ still cannot use TLS if
  the APs run older firmware.
- **The spool filename carries a config hash.** It changes when the config is regenerated — the
  fastest way to confirm a change actually took effect.
- **A ProductSection already in an exported OVF is stale.** The injector now replaces it instead of
  skipping it — never hand-keep one. A kept section ships the old `s1collector` hostname default and
  undoes the unique-hostname fix.
- **The old §4.1 `hv-*` unit check fails on v8+ images because the units are gone.** That is correct,
  not a regression — Hyper-V support was dropped 2026-08-03. Do not chase it.

## 13. If you are an AI session picking this up

Read in this order: `HANDOFF.md`, then `claude/gold-build-progress.md` in the Claude project, then
the validation guide.

Things worth knowing about the working environment:

- **A cloud sandbox cannot reach `10.10.75.10` or the appliance.** They are private addresses. A
  connectivity test appears to succeed because an egress gateway intercepts every private IP and
  returns an identical response — verify with a known-bad address before trusting a result.
- **Claude in Chrome can reach them**, because it runs in the user's browser on their network. It
  **cannot** get past a self-signed certificate interstitial — Chrome's SSL warning is an error page
  the extension can neither screenshot nor click. A human clicks through once per browser.
- **Chrome's `file_upload` cannot see the Cowork folder bridge.** Datastore uploads need a human.
- **`s1-collector-web` runs standalone for testing.** Install `wordlist.txt` to
  `/usr/local/share/s1collector/`, run it as root, drive it with `curl -k` and a cookie jar. Both
  passphrase paths, the CSRF gate, the gated status rows and the sources form were all verified this
  way before anything touched a VM. Do this rather than testing on the appliance.
- **`tests/test_web.py` runs anywhere.** Run it before changing `s1-collector-web`.
- **Validate every seed ISO by extracting it**, not by trusting the build: `xorriso -osirrox on`,
  parse `user-data` as YAML, unpack the embedded kit, `bash -n` every shell script and `ast.parse`
  every Python one, then sweep for credentials. Every seed in §3 was checked this way.
- **Do not guess at a cause when you can measure one.** This project lost a full build cycle to a
  confident guess that a ufw block was a certificate warning. Ask for `ufw status`, `ss -ltnp` and
  the build log before forming a theory.
- **Write findings to the build log and to this file as you go**, not to chat. That was an explicit
  request.
