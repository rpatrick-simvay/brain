## 1. Purpose

Simvay's renewal exposure is spread across many small product contracts per client (S1, A1, KB4, EMTS, ECRM, M365, Mimecast, Umbrella, DUO, VEEAM, C2, etc.). Contracts expire, successors are sometimes entered late or not at all, and HaloPSA automation occasionally spawns duplicate contract records and duplicate renewal opportunities. This report gives ops and leadership one weekly, evidence-backed view of: what expired and whether it was truly renewed, what is coming due in the next 90 days and whether a quote covers it, where duplicates and data-hygiene problems are, and whether every EMTS client also carries Action1. **v2.1 added a week-over-week progress layer: every row touched in the last 7 days is visibly highlighted (§6a). v2.2 makes Section 1 a working list rather than an archive: only rows that are still outstanding, plus rows that resolved during the week (shown once, highlighted, then dropped) — see §6.1.**

The value of the run is the **notification** it produces when something needs a human — not the transcript. See §9.

## 4. Data pulls (re-pull fresh every run)

Large results are saved to a file on disk automatically when they exceed the inline token limit. **Never try to read a large Halo result inline** — parse the saved `.txt`/JSON with Bash + `python3` (`json.load`). Save a working copy of each pull into the run's working directory (`/root/renewals` on the 8/24, 8/31 and 9/06 sessions; `/home/claude/renewals` on 9/07 — the container's home directory varies, so use `pwd` rather than assuming).

1. **Contracts** — `halo_get` path `ClientContract`, query `{"count":500,"includeinactive":true,"includeexpired":true}`. Returns `{record_count, contracts:[…]}`. **197 records as of 2026-09-07 — unchanged since 8/24; zero new contract records entered in three consecutive weeks.** Key fields per contract: `id`, `client_name`, `ref`, `start_date`, `end_date`, `expired`, `active`, `contract_status`, **`last_modified` (needed for the v2.1 touched flags)**, and **`site_name`**. **Correction to a prior note (2026-09-07): `site_name` IS returned on the bulk `ClientContract` pull**, not only on `ClientContract/<id>` — c155 came back as "Court", c149 as "Main", c211 as empty, straight from the list call. No per-contract fetch is needed for the §5.9 multi-entity check.
2. **All sales opportunities** — `halo_get` path `Tickets`, query `{"domain":"opps","includeclosed":true,"pageinate":true,"page_size":50,"page_no":N}` for **every** page (as of 2026-09-07 that is pages 1–6, `record_count` = **285**, unchanged from 9/06). Loop until you have all `record_count` tickets. Save each page; combine into one compact array keeping: `id`, `summary`, `client_name`, `client_id`, `status_id`, `dateoccurred`, `dateclosed`, `contract_id`, `oppvalue`, `oppclosurecategory`, `pipeline_stage_id`, `lastactiondate`. **A page call occasionally times out at 60s — just re-issue that one page; it succeeds on retry** (no timeouts on the 9/07 run; all six pages returned first time). Note: on the `domain=opps` path `halo_get` pages correctly and `record_count` IS the true total — unlike the plain ticket path, where it caps at 50 and ignores `page_no` (Runbook 12 §9.2).
3. **Identify renewal opps** — summaries matching the pattern `<ITEM>-MMDDYY-MMDDYY` (item code + term start/end) **plus** any summary containing `RENEWAL`. Normalize product prefixes and watch for the **"Domian Registration"** typo variant and spacing variants (`S1 - 070125 - 073026`). **Note: a renewal can also close under a summary matching neither pattern** — CMNH's "SentinelOne Managed SIEM - FY27" (opp 50889, $47,875 win) and Russell Township's "MTS Agreement 2026" (opp 50438, $40,904.55 win) both carried no pattern. Skim opps closed in the window for won deals even when they don't pattern-match. **The same applies to LOSSES: Thogus' two 8/31 losses (51414, 51420, $50,322.75 combined) match neither pattern.**
4. **Fetch ticket detail** — for open/unresolved renewal opps **and** any opp tied to a flagged contract (expired, or ending inside the 90-day horizon) **and** every opp opened or closed inside the touched window. Call `halo_get` `Tickets/<id>` with query `{"includedetails":true}` and read the embedded `quotations` (`id, title, status, date, expiry_date, approvalstate, so_number, revenue`), `salesorders`, and `closure_note`. Each full ticket is ~180 KB and will be saved to disk — parse the saved file, extract only the fields above.
   - **Parallelize:** spawn general-purpose subagents in batches of ~13–15 tickets each. Each subagent must return **compact JSON only**, never the raw 180 KB, and must be told explicitly that the "exceeds maximum allowed tokens" error is expected and that it should parse the saved file with `python3` rather than the Read tool. **Pass absolute output paths** (subagents resolve `~` differently) and verify the files exist before merging.
   - **The newest-110 quote pull collapses the workload dramatically (proven again 2026-09-07).** With the quote layer already in hand, only **43 tickets** needed detail (three batches, ~2 min wall clock) versus 92–105 on prior runs, and the batches served only to confirm the zero-quote opps were genuinely empty and to catch pre-window quotes such as Olmsted Township's 10052. Do this: pull the quotes first, then batch only the opps whose quotes would be older than the pull's floor plus the opps you expect to be empty.
   - **If a ticket payload has no embedded `quotations`/`salesorders`**, fetch them separately from `Quotation?ticket_id=<id>` and `SalesOrder?ticket_id=<id>`. **This is common, not exceptional.** **Sanity-check the merge:** count how many tickets came back with quotes per batch; a batch that is suspiciously quote-free fetched them wrong. On 9/07 batch B returned 1 of 14 with quotes and that was CORRECT — the 13 quote-free tickets were all automation-spawned Stale opps.
   - **`quotation_count` and `salesorder_count` are trustworthy shortcuts (discovered 2026-09-07).** Both scalars appear on every `Tickets/<id>` payload and matched the separate `Quotation?ticket_id=` / `SalesOrder?ticket_id=` lookups exactly in all 43 cases. Read the count first and skip the fallback fetch when it is 0 — it saves roughly one call per ticket.
   - **Faster alternative for the quote layer (proven 2026-09-06 and 2026-09-07):** one call to `halo_get` path `Quotation` with `{"count":110,"order":"id","orderdesc":true}` returns the newest 110 quotes (~300 KB, saved to disk) with `ticket_id`, `status`, `approvalstate`, `so_number`, `revenue`, `date`, `expiry_date`. **Do not ask for more than ~110 — `count:300` came back truncated at 500,000 characters and would not parse.** Returns `{record_count, quotes:[…]}` (key is `quotes`, not `quotations`). On 9/07 this covered ids 10166–10289, i.e. every quote since 2026-06-26.
   - **NEW 2026-08-31 — the ticket detail payload does NOT carry every field the opps listing does.** `oppvalue`, `oppclosurecategory` and `dateclosed` are variously absent from `Tickets/<id>`; the payload has `oppvalueadjusted` instead of `oppvalue` and no closure category at all. **Take `oppclosurecategory`, `dateclosed` and `oppvalue` from the `domain=opps` listing.** Do not let a subagent's null overwrite a good listing value.
   - **`closure_note` is effectively unavailable (confirmed hard on 2026-09-07).** Across all 43 tickets in three independent batches the field was either an empty string or absent from the key set entirely — including on genuinely closed opps. Two subagents searched for `closure`/`resolution`/`solution` variants and found only `elapsed_resolution_hours`. **Stop treating `closure_note` as an evidence source.** Loss and decline reasoning must come from `oppclosurecategory` on the listing plus ticket notes; if closure text is ever needed, try `get_ticket_actions` rather than the ticket record. Say so on the Method page as a caveat.
   - Note: HaloPSA sales-order objects have no `so_number` or `total` field — the SO's `id` **is** the number (quotation `so_number` "4087" ↔ salesorder id 4087), and the total-like field is `revenue`. `SalesOrder/<id>` also carries `po_number`, `invoice_count`, `note` and `site_name`, useful when tracing which entity an order belongs to.
   - **Never sum multiple quotes on one opportunity.** World Shipping opp 51949 carries four quotes dated 8/31 — 10285 (SENT), 10284 and 10281 (drafts) and 10282 (superseded) — three of them at the same $14,312. Summing them triple-counts. Pick the live one per opp. The same discipline applies across opps for deliberate alternatives such as Solon's 10257/10258.

## 5. Matching rules (confirmed with Ryan 2026-07-17; additions dated)

Apply these exactly. A verdict must rest on positive evidence, not absence of contradiction.

1. **Renewed only with positive evidence.** An expired contract counts as renewed only if one of these holds:
   - a **successor contract** for the same client + same product whose term **starts within ±60 days** of the old end date (or already overlaps past it); **or**
   - the contract is flagged **"Live + Renewed"**; **or**
   - an **accepted quote** (approvalstate 2 or a sales-order number) converted to a **sales order**.
   - **Product-prefix variants count.** Before calling RECORD GAP or LAPSED, scan the client's live contracts for a *variant* ref, not just an exact prefix match — Russell Township's Police M365 successor is `M365-PD-072126-072027` (c179), and Parma Heights' Mimecast successor is the **typo ref `Mimescast-052926-052827` (c190)**, both of which a strict prefix match misses.
2. **Microsoft roll-up.** Microsoft cloud products (Intune, Entra, Defender, etc.) count as renewed if the client has a **more recent M365 licensing contract** — they roll into the master. Cite the master contract as evidence. **Caution added 8/31: the roll-up only works if the master is itself live.** GLB's CoPilot c81 could not roll into c122 because c122 expired the same week — and with c122 now Expired too, GLB has no live master at all.
3. **EMTS ↔ Action1 (A1).** Every client with a live EMTS contract should also hold a live Action1 contract. When A1 is missing, distinguish **"A1 expired on `<date>`"** vs **"A1 never existed in Halo"** vs **"A1 quote sent, no contract record yet."** **Scope clarified by Ryan 2026-09-06:**
   - **EMNS clients are OUT of scope.** EMNS is managed networks — a very small-scope service with nothing to do with the managed-technology playbook or managed security. EMNS clients would not have Action1. The 8/3 open question is closed: do not widen the rule, and do not list Solon City Schools (c45/c46) or any other EMNS-only client in Section 4.
   - **MTS clients are COVERED by their MTS contract.** MTS is the offering for very small clients and rolls the tech-stack software (Action1 included) into the contract price, so an MTS client with no standalone A1 record is **OK — included in MTS**, not a gap. Aria Financial Group is MTS; cite its MTS/EMTS contract as the evidence.
   - **A not-yet-started EMTS term is a gap with a start date, not an active gap.** Staffco (c221, starts 10/1/26) is a genuine gap but is reported as "FLAG — starts `<date>`, bundle A1 before start", and only escalates once the term is live without A1.
   - **An expired EMTS record whose A1 line is current is not a Section 4 problem** (added 2026-09-07). Parma Heights' EMTS c30/c31 expired 8/31 while A1 c218 renewed on 8/17 through 2027-08-16 — the A1 line is *ahead* of the EMTS record, not behind it. Report A1 as OK and leave the EMTS term to Section 1.
4. **Upcoming horizon = 90 days.**
5. **Exclusions.** Drop Simvay-internal **TEST** records and template records (e.g. "Template Pre Pay"). Report **duplicate** contract records in the Duplicates section, not as expired-vs-successor rows.
6. **Report each contract once.** Where a term was extended by a `.2` record (e.g. Huron S1 c58 → c187), collapse the pair into a single row citing both ids rather than two near-identical rows. Do not repeat an expired contract in Section 2 just because its renewal is unquoted — Section 1 already carries it. Likewise collapse base+expansion pairs (EMTS + EMTS-EXP) into one row.
7. **A prior "SUPERSEDED — VERIFY" evidence record can disappear.** c191 (Russell Township MSA) was the cited evidence for four SUPERSEDED rows and was **deleted** during the 8/24 week. Always re-confirm that a cited successor still exists in the fresh pull before repeating last week's verdict.
8. **Do not trust a prior week's *identification* either, only its evidence (2026-08-31).** Runbook 12 §12 recorded on 08-26 that "the only CoPilot contract is #171 and it belongs to Conveyer & Caster, not GLB." That was wrong: **c81 `M365 CoPilot-110124-082626` is Great Lakes Brewing's**, and it lapsed on 8/26 while the note said there was nothing to worry about. Re-derive contract identity from the fresh pull by client + ref every run; never carry an identification forward on trust.
9. **Multi-entity clients: a same-product successor is only a successor for the same entity (Ryan, 2026-09-06).** City of Avon Lake carries **three separate VEEAM contracts — PD, City and Court** — and the Court line can never be rolled into the others because it is billed separately for funding reasons. The ref does not distinguish them; **`site_name` does, and it comes back on the bulk contract pull** (c155 = "Court", c149 = "Main", c211 = empty). Do not match a successor across sites. Expect the same pattern on any client with PD/Fire/Court sites.
10. **DECLINED/CANCELLED — CONFIRM requires a closure note or a client statement (Ryan, 2026-09-06).** Status 19 Rejected on the opp, or an expired quote, is not enough — either can be the workflow's response to an unaccepted quote. Without positive evidence of a decline the row is **EXPIRED QUOTE → RE-QUOTE**, not DECLINED. **Given that `closure_note` is effectively always empty (§4.4), this rule means DECLINED should almost never be issued from data alone — it needs Ryan.**
11. **Verified-closed items stay closed (Ryan, 2026-09-06).** Once Ryan has confirmed an expired contract as fully closed (client departed, product cancelled, or superseded), record it in §11 under "Confirmed closed — do not re-list" and never surface it in Section 1 again, even though the expired record remains in Halo. **One exception, settled 2026-09-07: the run that FIRST reports the confirmation tables it once as a resolved-this-week row (§6a), then it drops off permanently.** The confirmation is the resolution event and has to reach the report once.

### 6a. v2.1 — touched-row highlighting (week-over-week progress)

Every row in every section is checked for **activity in the last 7 days** (the touched window, §3). A row is **touched** when any contract, opportunity, quote **or sales order** it references had activity in the window:

- contract `last_modified` in window (covers new/edited records);
- opp `dateclosed` or `dateoccurred` in window (closed, merged, or newly spawned);
- any embedded quotation `date` in window (quote raised/sent);
- **any embedded sales-order `date` in window** (added 2026-08-03 — a renewal can be *won* in the window off a quote raised earlier).

**Mapping matters:** extract every `cNNN` and 5-digit opp id from the row, **and** expand each contract id to its linked opps (`contract_id` on the opp) — some rows describe a quote without naming the opp id.

**Presentation (identical rule in PDF and Excel):** the **whole row** gets a green wash `#E8F4EC`; the first cell gets a 3px left accent `#2E7D4F` (PDF) / bold text (Excel). Verdict cell colors sit on top unchanged. Every section carries a legend line, page 1's meta strip explains the convention, and the Method page ends with a "Week-over-week: N of M rows" KPI bar. Counts by run: **42 of 92 (2026-07-31), 21 of 102 (2026-08-03), 13 of 107 (2026-08-10), 11 of 87 (2026-08-17), 22 of 94 (2026-08-24), 12 of 92 (2026-08-31)** — a quiet week reads as a low count, which is itself the signal. **From v2.2 the denominator shrinks (Section 1 no longer tables the matched tail), so do not compare v2.2 counts to the series above without noting the scope change.** First v2.2 count: **23 of 70 (2026-09-07)** — S1 11/18, S2 5/26, S3 1/6, S4 3/8, S5 3/12.

**Section 1's wash means something different from the other sections (settled 2026-09-07).** §6.1 defines it as "resolved this week", but a row that *became* outstanding in the window is equally this week's news, and on 9/07 six of the eleven washed Section 1 rows were newly-expired terms. The rule now applied: **in Section 1 the wash means the row changed state this week — it either became outstanding or it resolved**; in Sections 2–5 it keeps the strict data-activity meaning above. Say so in the Section 1 legend AND on the Method page, because the two meanings sit inside one workbook and a reader will otherwise assume they match.

**Read the count PER SECTION, not just in total (2026-08-31).** The 8/31 run was 12 of 92 overall, but the distribution was the finding: **Section 2 scored 0 of 26.** A zero in Section 2 is a louder signal than a low total and belongs in the "What changed" block. ## 12. Troubleshooting

- **Halo result "exceeds maximum allowed tokens":** expected for contracts, opp pages, quotes and ticket details. Read the saved file path from the tool result and parse with `python3`; never re-request inline. Try `json.load` first and fall back to `raw_decode` only if it throws — on 8/24, 8/31, 9/06 and 9/07 every payload was clean, well-formed JSON **except a `Quotation` pull with `count:300`, which was cut at 500,000 characters; keep quote pulls to ~110.**
- **The contracts payload is a DICT, not a list:** `json.load` returns `{record_count, contracts}`. Unwrap `raw["contracts"]` (or `raw["tickets"]` on the opps path, `raw["quotes"]` on the Quotation path) before iterating, or every `.get()` throws `AttributeError: 'str' object has no attribute 'get'`.
- **A `halo_get` page call times out after 60s:** transient. Re-issue that single page.
- **Opp pages look short:** loop `page_no` until the number of collected tickets equals `record_count`. A missing final page silently drops renewals.
- **Subagent returns huge output:** it fetched detail inline. Re-run that batch instructing compact-JSON-only returns.
- **A batch comes back with almost no quotes:** check `quotation_count` before assuming a fetch error — on 9/07 a batch returning 1 of 14 was correct, because 13 of its tickets were automation-spawned Stale opps that genuinely have no quotes. ## 15. Export — the connected local folder (Ryan's decision, 2026-08-24)

**The deliverables are exported by writing them into a local folder joined to the session.** This replaces the SharePoint upload block that was in the task prompt from 08-20 to 08-24.

**How.** After `SendUserFile`, check whether a local folder is connected (the session reminders list them; `mcp__remote-devices__get_device_info` reports `connectedFolders`). If one is, write both files into it with **`mcp__remote-devices__device_commit_files`**, named exactly `Simvay_Weekly_Renewals_v2.2_<YYYY-MM-DD>.pdf` and `.xlsx`. It takes a staged file rather than inline base64, so the payload-size problem below simply does not arise. If Ryan has joined a OneDrive/SharePoint-synced folder, sync performs the SharePoint filing with no upload tool involved. **Known target (9/06): Ryan's connected folder `LeadershipHub - Documents\Reports` holds `Operations\` (current week) and `Operations\Previous Weeks\` (archive) — the 8/31 PDF is at `Operations\Simvay_Weekly_Renewals_v2.1_2026-08-31.pdf`.**

**If no folder is connected — the normal unattended case — skip the export.** A scheduled firing runs in the cloud with no desktop bridge, so local folders are never attached to it. This is NOT a failure: do not stop, do not retry, do not describe the run as incomplete. Add one sentence to the notification saying the files are in the conversation and were not exported because no folder was attached. A *genuine* export failure — folder connected, write refused or errored — must be reported plainly.
